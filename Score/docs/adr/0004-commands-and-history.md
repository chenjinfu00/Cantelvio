# 0004. 所有修改都是确定性的可序列化命令

- 状态：已接受
- 日期：2026-10-01

## 背景

撤销/重做、AI 生成的补丁、版本历史、实时协作都需要“修改”本身是可记录、可传输、可重放的对象。

## 决定

- `Command` 是纯 JSON 的联合类型（`core/src/commands/types.ts`），是修改文档的**唯一**方式。
- 命令是**确定性**的：新元素的 id 由调用方生成并写进命令；处理函数里不允许 `Date.now()`、
  `Math.random()`、I/O。
- 处理函数在 immer 草稿上修改，`produceWithPatches` 产出 patches 和反向 patches；
  `Session` 用它们实现撤销/重做（并保存撤销前后编辑器的选择与光标）。
- 非法命令抛 `CommandError`，文档不变；批处理命令要么全部成功要么全部不生效。
- 编辑器的“操作”（actions）负责从用户意图生成命令（例如计算音高、生成 id、需要时追加小节）。

## 后果

- AIlegro 的结果导入就是一批命令（`planComposeImport` 返回 `Command[]`），自然地成为一个撤销步骤。
- 协作可以采用“服务器排序 + 客户端重放”（见 [collaboration-and-history.md](../collaboration-and-history.md)）。
- 每个新编辑功能都要：命令类型 + 处理函数 + 测试；比直接改状态多写一点，但换来可靠性。
- 携带“推导数据”的命令（如改拍号需要的新小节 id 数量）在协作重放时可能需要重新生成。

## 考虑过的其他方案

- 直接修改可变状态 + 快照撤销：简单，但无法支撑协作和语义历史。
- CRDT 文档（Yjs/Automerge）：合并自动，但难以保持乐谱不变量（声部内不重叠、小节结构）。
