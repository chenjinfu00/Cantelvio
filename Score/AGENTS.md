# AGENTS.md — instructions for AI coding agents (Codex, Claude, …)

AIlegro Score is a web-based music notation editor (piano, chamber music, orchestral scores) in
the spirit of Sibelius/MuseScore, with its own engraving engine and a first-class bridge to
**AIlegro**, the owner's AI composition system (a separate project in the sibling folder
`../Compose`). Spell the names exactly: **AIlegro**, **AIlegro Score**.

The human owner reads Chinese; docs under `docs/` are mostly Chinese. Code, identifiers, comments,
commit messages and this file are English.

## Read before you change anything

1. `docs/roadmap.md` — current status, milestones and the task list (task ids like `M2-ENG-03`).
2. `docs/architecture.md` — packages, data flow, invariants.
3. `docs/score-model.md` — the document model (the most important contract).
4. The doc for the area you touch: `docs/engraving.md`, `docs/ailegro-integration.md`,
   `docs/editor.md`, `docs/collaboration-and-history.md`, `docs/text-notation.md`.
5. `docs/adr/` — decisions already taken. Do not silently reverse one; write a new ADR.

## Repository map

| Path | What it is |
| --- | --- |
| `packages/core` | Score model, rational time, pitch spelling, instruments/templates, **commands** + undo/redo, JSON file format, text notation, MusicXML import, playback timeline. Pure TS. |
| `packages/engraving` | Layout engine: ScoreDoc → pages of positioned graphics → SVG, using SMuFL/Bravura metrics. Pure TS. |
| `packages/ailegro-bridge` | AIlegro interchange: score-record export, compose requests, import of generated music. Pure TS. |
| `apps/web` | React + Vite editor UI (store, keyboard input, palettes, playback). |
| `tools/` | Node CLIs (e.g. `render-score.ts` renders samples/files to SVG/PNG). |
| `docs/` | Design docs, ADRs, roadmap. |

## Commands

```sh
npm install            # Node >= 22.12
npm run dev            # editor at http://127.0.0.1:5178/
npm run check          # lint + typecheck + unit tests — must pass before every commit
npm run build          # production build of the editor
npm run render -- --sample orchestra --out out/   # headless SVG/PNG render for visual checks
npm run ailegro:serve  # local AIlegro service (../Compose): compose, analysis, PDF/recording imports
npm run test:adapter   # Python tests of the adapter's import jobs (stand-in tools)
npm run gen:smufl      # regenerate SMuFL glyph data (only when changing fonts/glyph lists)
```

## Architecture invariants (do not break)

1. **The ScoreDoc is the single source of truth.** Engraving, playback, export and UI are derived.
2. **Every change goes through a command** (`packages/core/src/commands`). Never mutate a
   document directly. A new editing feature = new command type + handler + tests.
3. **Commands are deterministic and serializable.** Ids for new elements are generated by the
   caller and passed in the payload. No `Date.now()`, `Math.random()` or I/O inside handlers.
   This is what makes undo/redo, AI patches, version history and collaboration possible.
4. **Musical time is exact.** Use `Rational` (whole-note units, quarter = 1/4). Floats are only
   for geometry and audio seconds.
5. **Concert pitch with spelling** is stored (`{step, alter, octave}`). Written pitch for
   transposing instruments is derived by diatonic transposition.
6. **One sounding note = one event**; ties at barlines are derived by the engraver. Rests are
   implicit gaps. See `docs/score-model.md` before touching events.
7. **`packages/*` are pure**: no DOM, no Node APIs, no React. Enforced by `packages/tsconfig.json`
   (no DOM lib) and ESLint. Browser/Node specifics live in `apps/web` and `tools/`.
8. **Engraving is a pure, deterministic function** `(doc, options) → layout → SVG`. Same input,
   same bytes. This keeps snapshot tests and visual diffs meaningful.
9. **Versioned contracts**: the `.ailegro.json` file format and the AIlegro interchange schemas
   (`ailegro.score-record/1`, `ailegro.compose-request/1`, `ailegro.compose-result/1`,
   `ailegro.analysis-request/1`, `ailegro.analysis-result/1`) only change with a version bump, a
   migration, tests and a doc update.
10. **i18n**: every UI string goes through `apps/web/src/i18n` with both `zh` and `en`.

## Working rules

- Keep changes focused; one task per branch/PR. Prefer small, reviewable commits.
- Write tests next to the code (`*.test.ts`). Commands and engraving rules need unit tests.
- Visual/engraving changes: run `npm run render` for the affected samples and look at the PNGs.
  Mention what you checked in the PR description; attach before/after images when possible.
- Do not add dependencies casually. Pure packages should stay dependency-light (core: immer).
- Generated files end in `.generated.ts`; regenerate them with the script, never hand-edit.
- When you finish a roadmap task, update its status in `docs/roadmap.md`. Record decisions with
  real trade-offs as a new ADR in `docs/adr/`.
- Never commit `node_modules`, `dist`, `out/`, renders, local scores or secrets.

## Git conventions

- Default branch: `main`. Branch names: `feat/<scope>-<slug>`, `fix/<scope>-<slug>`,
  `docs/<slug>`, `chore/<slug>`; agent branches: `codex/<task-id>-<slug>`, `claude/<task-id>-<slug>`.
- Conventional Commits: `feat(engraving): beam 16ths across beat pairs`,
  `fix(core): keep ties when re-barring`, `docs: …`, `test: …`, `chore: …`, `refactor: …`.
  Scopes: `core`, `engraving`, `bridge`, `web`, `tools`, `docs`, `ci`.
- `npm run check` must be green before committing. Rebase on `main` before opening a PR.
- Details (PR flow, releases, tags, working alongside Claude/Codex): `docs/git-workflow.md`.

## Environment notes

- The working copy is a local folder (`~/software develop/Cantelvio/Score`, not in a synced drive),
  next to `../Compose`. GitHub (the remote) is the source of truth; `npm install` artifacts stay
  local. Never create file names containing spaces: names like `name 2.ext` are sync-conflict
  copies (git-ignored) — report them, do not commit or delete them silently.
- Install dependencies on the machine that runs them. Never run `npm install` for this folder from
  a Linux VM or sandbox: esbuild, rollup and sharp ship platform-specific binaries.
- The sibling `../Compose` project has its own `AGENTS.md`. Do not modify it from this repository;
  integrate only through the contract in `docs/ailegro-integration.md` and `packages/ailegro-bridge`.
