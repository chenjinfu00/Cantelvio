# AIlegro 与 AIlegro Score 联合开发计划

日期：2026-10-05。状态：开发计划，新增引擎与下列待做功能尚未实现。首期目标由用户确认：给定旋律，生成合适的伴奏。

把 AIlegro 发展成可以利用多个音乐模型和工具的生成系统，把 AIlegro Score 作为输入、编辑、审阅和输出乐谱的工作台。先完成旋律配伴奏的一条完整流程，再扩展续写、配器、连续演奏和完整作品生成。已有自训练模型保留为基线；实际采用哪个引擎，由音乐效果、控制能力、速度和许可共同决定。

本计划是两边共同的产品与接入顺序。Score 的具体任务见[编辑器实施计划](../Score/docs/open-source-integration-plan.md)，模型实验细节见[旋律配伴奏路线图](training/MELODY-ACCOMPANIMENT-ROADMAP.md)，软件版本、许可、下载状态见[开源资源清单](OPEN-SOURCE-INVENTORY.md)。三份文件分别回答“做成什么”“怎样验证模型”“资源是否已准备好”。

## 两个项目怎样分工

| 工作 | 所属项目 | 交付边界 |
| --- | --- | --- |
| 模型加载、条件生成、候选评分、连续续写、推理加速 | AIlegro | 固定版本的生成引擎，通过服务返回音符与来源；不直接修改用户的 ScoreDoc |
| 和声分析、录音转写、语料整理、标注和评估 | AIlegro | 分别提供分析、转写和离线处理能力；分析建议与原始材料分开保留 |
| 写谱、改音、选范围、锁定材料、目标乐器、候选比较和接受 | AIlegro Score | 所有用户编辑和接受操作通过可撤销命令完成 |
| 排版、分谱、回放、保存、MIDI / MusicXML / PDF 导出 | AIlegro Score | 从同一份 ScoreDoc 推导，开源回放和导出库接在浏览器或工具层 |
| 交换契约和参考适配器 | 两边约定，Score 维护契约实现 | 保留版本化 JSON；适配器调用各引擎，两个项目各自维护自己的实现 |

保留 Score 自研排版、实际音高、精确有理数时间和命令系统；未来协作沿用服务器排序的命令日志。新增第三方工具先放在边界模块，避免把 TensorFlow、模型词表或浏览器依赖引入核心乐谱模型。

## 用户要得到的完整流程

```mermaid
flowchart LR
  input["手写旋律 / MusicXML / PDF / 录音"] --> edit["Score 校对与编辑"]
  edit --> request["选范围 · 锁定材料 · 目标乐器"]
  request --> engine["AIlegro 分析与生成引擎"]
  engine --> candidates["候选试听与比较"]
  candidates --> accept["按小节或乐器接受"]
  accept --> work["Score 继续修改 · 回放 · 导出"]
  work --> request
```

第一条流程用 8–16 小节旋律配钢琴伴奏。输入可以直接在 Score 写，也可以导入 MusicXML。PDF 和录音导入必须先校对识别结果，不能把识别错误当作作曲条件或真实标签。用户改一个和弦、某个小节或一个乐器后，只重写选定且未锁定的范围；原旋律和其他已确认音乐保留。

主操作对象是六组乐器：木管、铜管、打击乐、竖琴／键盘、高音弦乐、低音弦乐。Score 再把组映射到具体声部；钢琴是键盘组中的具体目标。低音、和声、旋律身份可用于内部生成和分析，避免让用户重复操作三套角色栏。和弦建议和人工修改入口保留为可选的高级操作。允许某组参与生成与要求该组必须发声，需明确区分。

候选阶段应可切换、试听、拒绝；接受后成为能继续编辑的音乐。重新生成时用当前已确认乐谱构建新请求，未接受候选默认不作为新材料。命名版本与局部接受是待做功能；当前只有会话撤销和整批接受。

## 开源项目接到哪里

| 能力 | 拟使用的项目 | 已有基础 / 下一步 |
| --- | --- | --- |
| 条件伴奏与补全 | 自有 v3.1；[AMT](https://github.com/jthickstun/anticipation) | v3.1 已有 Score 适配器；AMT 代码和 10 个权重快照已完整下载、校验，但尚未在本机生成。先跑条件生成对照，再决定开放为可选引擎或用于改进自有模型 |
| 连续演奏 | 当前 v2；通过验证后的 v3.1 或 AMT | 主页 v2 与 Score v3.1 是不同路径。统一服务边界和事件约定后逐个迁移，不能把 Score 的改进算成主页已生效 |
| 和声分析与标签统一 | 自有配和声 / 分析模型；[AugmentedNet](https://github.com/napulen/AugmentedNet) | 自有模型已有接口；AugmentedNet 已下载，环境和推理待验证。先抽样核对，再生成带来源的标注 sidecar；人工、模型和旧标签保留各自来源 |
| 录音变成可编辑材料 | MuScriptor + Beat This!；[Basic Pitch](https://github.com/spotify/basic-pitch) 作为单乐器备用 | 前者已有转写脚本和导入服务，真实录音基准未完成；后者已下载待验证。MuScriptor 权重有非商用条件，不可默认作为商业版本引擎 |
| PDF / 图片变成曲谱 | Audiveris 外部程序 → MusicXML → Score | 外部程序接口已有；本机安装位置与真实识谱效果待确认。遵循现有 ADR，独立处理其 AGPL 许可义务 |
| 乐谱处理和交叉核对 | Symusic、Mido；[Partitura](https://github.com/CPJKU/partitura)、music21 | 前两者已有环境；Partitura 已下载，music21 未在已盘点本机环境安装。用于离线处理和导入交叉检查，ScoreDoc 仍是编辑器事实来源 |
| 扩大训练材料 | OpenScore Lieder；PDMX 筛选谱库 | 已有 Lieder 处理数据；PDMX 只有元数据与 77,321 条候选索引，曲谱未下载。先按目标编制选小批 MusicXML，检查许可、重复和旋律标注，再扩量 |
| 实际音符与真实录音评估 | mir_eval；MusicNet、Winterreise，ASAP 为候选 | 评估工具已准备；MusicNet 音频未取，Winterreise 已解压但未评估，ASAP 未下载。转写指标与作曲试听分开；作品与训练材料重叠需检查 |
| 回放和交付文件 | SpessaSynth + MuseScore General、@tonejs/midi、svg2pdf.js + jsPDF、Bravura、霞鹜文楷 | Score 回放、MIDI、矢量 PDF 已有接入代码。仍需多浏览器和大编制复验；MusicXML 导出、超过 15 个有音高声部的 MIDI 导出待做 |
| 后续性能与演奏跟随 | ONNX Runtime、Matchmaker | 候选。分别在当前机器验证一致性与延迟、真实演奏定位误差后再接入 |

开源资源的数量不是交付指标。第一期先使用已接通的组件做完整流程；不同时安装全部候选依赖。Levanter 保留为 AMT 训练参考，不把运行公开权重的验证扩大成重新训练 AMT。暂不迁移到 VexFlow / Verovio 排版或 Yjs 乐谱存储，原因和其他候选的状态见资源清单。

## 可替换的生成引擎

AIlegro 应提供共同的引擎接口：加载固定模型、报告能力、预检请求、生成候选、取消、释放资源。初始只注册当前可验证的引擎；AMT 的接入通过基准后再增加。界面根据服务报告的实际能力开放任务：不能因为 v3.1 支持五项任务，就把五项任务全部标成 AMT 已支持。

每次运行记录引擎名、权重 SHA256、代码版本、种子、采样参数、候选数、输入哈希与生成耗时。当前结果契约已能带模型名、检查点和 SHA256，可先用已有字段。模型来自独立运行快照，运行时不再依赖“最后修改的 weights.pt”；恢复训练也不改变正在使用的模型。

保留 `compose-request/1` 与 `compose-result/1` 的既有语义。引擎选择、后台作曲任务、进度和取消采用单独版本化服务协议；若新增材料或返回语义无法由现有契约表达，再明确设计新版本、迁移和测试。现在 `/compose` 仍是同步调用；已有后台任务只用于 PDF / 录音导入，不能直接宣称异步作曲已经完成。

各引擎必须说明时间、乐器、速度变化、延音和控制的可表达范围。AMT 的事件时间与 Score 有理数时间的转换单独验证；保持原始锁定材料，无法精确编码时报告近似误差或拒绝该设置，不能静默重写用户的旋律。生成质量评估应包含原旋律与伴奏一起播放的效果，避免旁路保留了旋律却没有正确让模型理解它。

## 按交付结果推进

| 阶段 | AIlegro 工作 | Score 工作 | 完成条件 |
| --- | --- | --- | --- |
| J1 旋律配伴奏的完整流程 | 固定 v3.1 基线；接通并校准已有冲突评分；比较少量候选的耗时和试听效果 | 六组与声部映射；锁定材料预检；生成前快照与过期结果检查；候选比较、局部接受、撤销；回放与导出复验 | 从输入旋律到修改后重新生成、保存、导出真实跑通，锁定音符与用户修改保持不变 |
| J2 AMT 作为实际候选引擎 | 建立隔离推理环境；先测较小的条件模型，再测 medium；同输入和时间预算对照 | 显示引擎能力、进度和取消；同一流程比较不同引擎结果 | 有可复现的速度、内存、条件误差与试听记录。达到任务门槛才接入，否则保留基线和失败记录 |
| J3 数据与模型改进 | 验证 AugmentedNet 标注映射；PDMX 小批清洗与作品级分集；必要时微调旋律条件分支 | 可编辑的分析建议；命名版本和语义对比；MusicXML 导出、MIDI 大编制能力 | 标签来源清楚，测试作品不参与调参；改进能在未调参材料上体现，交换与编辑无回归 |
| J4 连续生成与编制扩展 | 对验证通过的引擎保持续写上下文、提前准备后续片段；六组控制、跨段延音和停止处理 | 把完整片段带来源导入 Score；只提交确定的范围，保持编辑响应与增量排版 | 本机长时间试听符合播放预算；无跨段丢音、重复或停止后复活；已提交乐谱不被后续流覆盖 |
| J5 完整作品工作台 | 长乐句、重复与变化、段落计划、表现控制；按实测决定是否加大模型 | 分谱、歌词、多声部排版、版本管理；之后才扩协作和发布 | 能完成并编辑一首作品，内部结构与最终回放、导出一致 |

J1 与 J2 是当前首要范围：先拿到现有方案的真实基线，再比较 AMT。J3 的模型改造取决于对照发现的缺口，不预先承诺一定重写 Transformer。转写的真实录音评估可独立推进，不作为手写旋律第一条流程的前置条件。每阶段交付演示文件、验证报告和剩余问题；尚未测量环境兼容与运行速度，因此不承诺完成日期。

## 必须通过的检查

1. **原材料保持不变**：被锁定的音高、起音、时值、延音和声部逐项一致；不能只检查“旋律仍在”。检查模型转换与 Score 默认记谱量化两处，给定旋律使用原始精确事件，近似只作为明确的用户选项。
2. **返回、曲谱、MIDI、播放一致**：用同一实际音高与时间线交叉检查；移调乐器只在显示层转成记谱音高；打击乐检查 GM 键位。抽样验证合成器发声与预期音高，不能仅凭听起来有声音认定正确。
3. **候选可安全审阅**：请求保存文档和范围基线，结果到达时检查修改、锁定、声部和小节结构；取消或过期结果不能写回。局部接受是一批确定性命令，可一次撤销；跨小节音、记号和线条不能因只接受半个对象变成悬空数据。
4. **音乐效果和性能分开**：固定旋律、长度、编制、种子列表和预算，用同音色盲听伴奏贴合、声部连贯和重复度；音符冲突是诊断，合法不协和音不机械删除。记录冷启动与常驻推理的首段等待、P50/P95、峰值内存、密集乐段和编辑后重算耗时。
5. **来源可追溯**：代码、权重、音色、字体、乐谱和录音分别记录版本与许可。Winterreise 的 SC06 文件许可与发布说明冲突仍未解决；优先已标明的 HU33。研究用资料与拟商业产品素材分开。用户接受一次候选不等于授权把作品加入训练；回流训练须另有明确选择与来源记录。

连续演奏的初步性能目标沿用模型路线图：P95 生成耗时不超过对应播放时长的一半，作为待验证预算；它不是现有实测结论。离线伴奏另列首段等待与候选切换耗时，不拿实时指标替代可用性判断。

## 当前模型与训练选择

v3.1 标准配置为 **5,014,967 参数**，FP32 参数约 **20.06 MB**，本地参考权重文件约 20.14 MB。AMT 的下载文件大小与本项目参数规模不是同一概念；10 个快照的合计约 13.06 GB，不代表每次运行都加载这些模型。

可以保留当前结构继续训练，但应先修数据和标注、固定基线，并用独立运行目录保存新权重。若新增旋律条件分支，可以迁移兼容的旧主干权重；新增层需训练，优化器恢复与精确续训要分别核验。AMT 权重不能作为 v3.1 的续训检查点。新模型大小实现后重新计数，不能把建议的 600–800 万参数预算当作已完成模型。

用户自行启动训练的约定继续有效。本轮只更新联合计划、Score 任务与设计文档，没有启动训练、安装新环境或更换运行权重。
